# Fix Report - 三维模型改为表面盲文 + 底座图例，并修复泛化性

> 后续更新（v0.3.3）：TokenHub 现已支持纯文字生成 3D，本文第 84 行“TokenHub 3D 只接受图片”的结论已过时。新的生成式路线见 [2026-11-05-tokenhub-text-to-3d.md](2026-11-05-tokenhub-text-to-3d.md)；本文保留为当时的历史记录。

## 问题描述

线上版生成三维模型时出现两个问题：

1. **立牌过多**：每个部件名称都被做成一块竖立的小名牌，围绕模型插在底座上。模型本体没有触摸标注，盲文阅读被拆成“摸一堆牌子”，而不是“摸模型本身”。
2. **泛化性差**：上传尾翼图后，生成的不是一个可辨认的尾翼，而是一个球加几片放射状薄片。水杯、地球仪、台灯这类常见物体没有可靠的拆解规则，换个对象就可能崩。

用户提出的产品方向是：**让外部 AI 负责“像不像”的三维建模，我们的 Agent 负责所有盲人适配**（缩放、底座、朝向、盲文、二维码、可打印性与合规检查）。

## 问题根因

1. 早期实现把“每个部件都要有盲文”简化成“每个部件插一块立牌”。立牌实现简单、不依赖部件表面曲率，但它把标注从模型表面移开了，违背触觉教材“摸到哪、读到哪”的原则。
2. 泛化性差不是模型能力问题，而是**中间表示太弱**：当时只有球、圆柱、盒子等少量图元，机翼类薄壁结构只能用薄板拼；提示词也没有告诉模型“尾翼应该用一个轮廓拉伸体（profile）”。
3. 部件的 `name_zh` 在表面放不下时被静默截断（例如“核心”变成“核”），导致表面标注失真。正确做法是：**能放就放全名，放不下就转到基地图例，不截断部件名**。
4. 太阳系行星直径只有 9–25 mm，而中文盲文名称需要 25–53 mm，行星表面物理上放不下，必须把名称放到连续的底座外缘，而不是给每颗行星插牌。
5. 重建网格来自第三方图生 3D，没有可靠的部件语义和坐标，无法判断“哪块表面属于翅膀”，因此在表面刻猜出来的名字会误导用户。

## 最终方案

### 1. 表面优先的盲文标注

新增并按形状选择表面标注策略：

| 形状 | 标注位置 | 说明 |
| --- | --- | --- |
| `sphere` | 球冠 `sphere_cap` | 直径 ≥ 7 mm 才尝试 |
| `cylinder` / `cone` / `tube` / `frustum` | 圆柱或锥台侧壁 `wall` | 高度 ≥ 盲文行高 + 2 mm 才尝试 |
| `box` / `plate` | 顶面 `top`，盒子失败后退到正面 `front` | 按可用长宽自动排版 |
| `profile` | 轮廓侧面 `profile_face` | 机翼、尾翼、鳍片、椅背 |
| 放不下 | 底座前缘图例 `base_legend` | 编号 + 全名，不截断 |

标注在部件的**局部坐标**里生成，再随部件一起旋转、倾斜、平移，因此盲文点始终贴着部件表面，不会悬空。

### 2. 删除所有竖立名牌

- 通用装配体、太阳系、重建模型三条路径的 `standing_flags` 统一为 `0`。
- 不再生成支撑柱、旗杆、悬空铭牌。
- 标题、二维码仍放在底座正面标签区，因为那是平面，属于真实的表面盲文。

### 3. 底座图例作为兜底

- 通用装配体：放不下的部件名按 `1部件名`、`2部件名` 的顺序刻在底座前缘。
- 太阳系：7 颗行星名称按离太阳由近到远的顺序，刻在底座外缘的圆柱面上；从正面标签牌左侧起绕底座一周摸读。底座厚度提高到 10 mm，保证 6.8 mm 高的盲文行放得下。
- 重建模型：标题在正面铭牌，特征名按编号刻在底座前缘；明确不在重建网格表面刻猜出来的名字。

### 4. 泛化性修复

- 图元扩展到 9 种：`sphere`、`cylinder`、`box`、`cone`、`frustum`、`tube`、`torus`、`plate`、`profile`。
- `profile` 用 8–16 个轮廓点沿 Y 轴拉伸，专门解决机翼、尾翼、鳍片、椅背这类“薄而有大轮廓”的零件，不再用小球和薄板硬拼。
- 提示词写入常用对象的正确拆法：
  - 尾翼/机翼 = 1 个 profile + 1 个机身圆柱；
  - 水杯 = tube 杯壁 + cylinder 杯底 + torus 杯柄（`tilt_deg=90`）；
  - 地球仪 = sphere 球体 + cylinder 支架 + torus 子午环 + cylinder 底座；
  - 台灯 = box/cylinder 底座 + cylinder 灯杆 + frustum 灯罩 + sphere 灯泡；
  - 火箭、椅子、花瓶、人物/动物也给出了体块拆解建议。
- 部件上限 12 个，超出时保留主要部件并写入警告，避免模型退化成“几十个小球”。

### 5. 重建打印的底座自适应

- 重建模型的特征名改到底座前缘图例，不再生成立牌。
- 图例列数、行距和底座前舌宽度联动计算；6 个长名称时会自动加宽前舌，避免两列盲文重叠。
- 底座半径上限 88 mm，配合 220 × 220 × 250 mm 的成型空间，保证加宽后仍能打印。
- 盲文标题放不下时只截标题，不截部件名。

## 验证结果

新增回归测试覆盖：

- 太阳系：`standing_flags == 0`、图例位于 `base_outer_wall`、7 个行星名按轨道顺序排列、每个名称都有盲文点。
- 尾翼：profile 翼型 + 机身圆柱可水密生成，尾翼标注在 `profile_face`，机身标注在 `wall`，无立牌，高度不超过 250 mm。
- 水杯、地球仪、台灯：三种配方均可水密生成，分别出现 `wall`、`sphere_cap`、`top` 表面标注，无立牌。
- 表面标注保留全名：`水杯 / 杯身 / 杯底 / 杯柄` 不被截断，放不下的两项进入底座图例。
- 13 个部件规范化为 12 个，并返回保留主要部件的警告。

全量结果：**273 项测试通过，32 项子测试通过**，耗时约 43 秒。

## 关于“外部 AI 建模 + 我们做盲人适配”的可行性判断

**结论：可行，而且这是比“让大模型直接吐 STL”更稳的架构。** 但要区分三种建模能力：

1. **图生 3D（照片 → GLB）**：现有 Tripo、Meshy、TokenHub 都能做，外形相似度明显高于提示词拼图元。我们已经有重建链路：提交图片、下载 GLB、解析网格、缩放、加底座、加盲文标题与图例、二维码、可打印性检查、导出 STL。这条路线可行性高，已经落地。
2. **文生 3D（一句话 → 网格）**：当前 TokenHub 的 3D 接口只接受图片，不接受纯文本；HY-3D 也不允许“提示词 + 图片”同时提交。所以“让接入的大模型直接按文字生成 3D”目前没有现成通道，需要新增 Meshy/Tripo 的文生 3D 适配器，或采用“文生图 → 图生 3D”的两段式。
3. **结构化规格（当前主路径）**：大模型输出部件、形状、相对大小和位置，编译器确定性地生成毫米级几何。它对教学模型、太阳系、分子、机械结构最可靠，盲文位置、底座、合规检查都可控。

**推荐的路由策略**：

- 教学示意图、太阳系、分子、机械结构 → 结构化规格编译器（当前路径，确定性最强）。
- 用户上传真实物体照片 → 图生 3D + 我们的盲人后处理（已实现）。
- 纯文字描述、没有参考图 → 先尝试结构化规格；失败再走“文生图 → 图生 3D”，并保留底座图例兜底。

**必须正视的限制**：第三方图生 3D 返回的是一个整体网格，没有“这是翅膀、那是杯柄”的语义分割和坐标。因此我们可以在网格上做统一的盲文标题、底座和方向适配，但**不能可靠地把部件名刻到它对应的表面**。要突破这一点，需要额外接入语义分割或部件级 3D 生成，成本明显更高。当前用“底座编号图例”是诚实且可用的折中。

## 经验教训

- 触觉教材的标注应该“跟着手走”，立牌是省事但错误的产品决策；当表面放不下时，底座图例比悬空铭牌更接近真实阅读习惯。
- 泛化性不能靠堆图元，要靠“图元 + 对象拆解配方 + 放不下时的降级路径”三层配合。
- 部件名不能被静默截断。截断会让盲文读出一个错误的词，比不标更糟；正确做法是整体转到图例。
- 生成式 3D 和确定性后处理应该分工：生成式负责“像”，确定性代码负责“能摸、能读、能打印、能合规”。把两者混在一起，任何一方出问题都会导致整条链路不可用。
