# Fix Report - 照片级重建丢失上下文、三视图被当成三个人物

日期：2026-11-08　范围：移动端 Web 应用「照片级三维重建」及同类模式

## Bug 描述

用户在线上用一张蓝色女仆的三视图测试照片级三维重建：

1. 第一次上传三视图，服务把每个视角都当成一个独立人物，生成了 3 个人物；模型出现 4 条腿、脸部损坏、手缺失，正视图还被对称补成了错误的反面。
2. 随后只用文字补充“这是三视图，是同一个角色的 3 个视角，请合成 1 个人物”，系统却提示缺少图片，无法重建。
3. 再上传同一张照片并附上这段文字，结果与第一次完全一致，文字没有产生任何作用。
4. 用户同时要求检查「触觉教材」和「触觉 3D 模型」两个模式是否存在同样的上下文断裂或强制上传问题。

## 问题根因

### 1. 每一轮对话在服务端都是无状态的

- 前端发送后立即清空 `state.files`，下一轮不会自动带上上一轮的照片。
- `/api/analyze` 每轮创建新草稿，只读取本轮的 `payload.files`；上一轮草稿的 `uploads/` 从未被读取。
- 模型规划只收到本轮文字，看不到“这是同一人物”“刚才那张图”等前文。
- 因此文字补充必然触发“至少需要一张照片”，用户只能重复上传。

### 2. 一张拼图被当成一张单视角照片

- `multiview_slots()` 只有在图片数量 ≥ 2 时才启用多视图；三视图拼图是一张文件，所以永远走单图 `image_to_3D`。
- TokenHub 的 Tripo 图生 3D 文档明确说明 `prompt` 仅用于文生 3D；图生 3D 不会把文字提示转发给几何生成。所以“这是同一个人”写在文字里也不会改变像素输入。
- 单图输入里同时存在正面、侧面、背面时，服务会把每个完整人形轮廓都当作一个物体，于是出现 3 个人物。

### 3. 照片重建本来就不能按文字改几何，但界面没有说清

- 图生 3D 的几何完全由照片决定；`prompt` 被忽略，`texture_prompt` 最多只影响纹理。
- 之前只写“尽量传给三维服务”，用户会合理地以为文字能改腿、手和脸。
- 界面没有“按文字重新生成”的明确选项，用户只能在照片模式里反复试。

### 4. 另外两个模式的同类问题

- 「触觉 3D 模型」：`plan_model3d()` 只收到本轮文字，像“把手臂加长”这样的追问会丢失上一轮的对象描述；生成式提示词也只拼接本轮文字。
- 「触觉教材」：追问“把开关移到右边”时没有复用上一轮的电路，只能重新生成整张场景；模型也只看到本轮文字。

## 尝试记录

### 尝试 1：在文字里反复强调“这是同一个人”

- 结果：失败
- 原因：TokenHub 图生 3D 不转发 `prompt`，文字无法改变几何；再次强调只会得到同一张输入图和同一个结果。

### 尝试 2：只让前端把上一轮文件重新发一遍

- 结果：不完整
- 原因：需要同时解决“服务端没有上一轮文件”“前端已清空文件”“模型看不到历史”三件事；只重发文件仍然会丢失上下文，而且同一张拼图还是会被当成单图。

### 尝试 3：把整张拼图直接当多视图提交

- 结果：不可行
- 原因：多视图接口要求按 `front/left/back/right` 分开的输入；整张拼图仍是一个文件，服务不会替我们裁切。

### 尝试 4：本地拆分拼图 + 明确的文字路线 + 多轮草稿沿用

- 结果：成功
- 原因：先用确定性图像处理把 2–4 个视角裁成独立文件，再交给多视图接口；同时让每轮草稿可以复用上一轮照片和历史文字；对无法拆分的拼图直接阻止提交，并明确告诉用户怎么改。

## 最终方案

### 多轮上下文与照片沿用

- 前端 `runTurn()` 在请求中带上 `reuse_draft_id` 和最近 6 条用户原话；`newChat()` 会清空这两项。
- 服务端新增 `_load_previous_draft()` 与 `_carry_over_images()`：同一产品、本轮没有新照片、且没有“换一个/重新做一个”等换对象语义时，把上一轮照片复制到新草稿，草稿保持自包含，原草稿不被修改。
- 新增 `context_text` / `context_previous`，把历史用户原话并入本轮要求。
- 「触觉 3D 模型」用累计上下文调用 `plan_model3d()` 和生成式提示词。
- 「触觉教材」把累计上下文交给 `generate_scene()`；对“把××移到××/改成××”这类追问，直接在上一轮电路上调用 `apply_scene_edit()`，并把修改项写进草稿。

### 三视图拼图自动拆分

- `reconstruct.split_multiview_sheet()`：在本地用 Pillow 估计背景色、按列检测 2–4 个尺寸相近的面板、裁成独立 JPEG。
- 拆分文件按 `front/left/back/right` 命名，`multiview_slots()` 会据此走 TokenHub 多视图请求。
- 原拼图标记 `skip_for_reconstruction`，构建时只发裁剪后的视角，不再整张发送。
- 拆分失败且文字/视觉判断表明是多视角时，草稿标记 `sheet_blocked`，禁止提交并给出“拆成 2–4 张单独照片”的具体指引。
- 拆分成功的判断会写进笔记、`model_spec.json`、`reconstruction.json` 和合规报告 `reconstruction.multiview`。

### 文字改写与重建方式

- 照片重建明确说明“以照片为准，文字不会保证改变几何”，这些调整只进入计划和报告。
- 新增 `generation_route`：`photo` 或 `text`。选择 `text` 时改走文生 3D，明确提示“外观会变”；只有配置了文生 3D 才能选择。
- 前端表单新增「重建方式」下拉框；构建按钮的可用状态和提交字段都会读取这个选择。
- 只上传文字、没有照片且文生 3D 已配置时，默认走文字路线，不再强制要求上传照片。

## 已知限制

- 拼图拆分按“从左到右 = front/left/back”处理；如果原图顺序不同，界面会提示分别上传并用文件名标注视角。
- 拆分依赖背景相对干净、视角之间有空白间隔；不满足时会阻止提交，而不是退回“整张图重建”。
- 图生 3D 仍无法修复照片里不存在的信息；正视图被对称补全属于服务端模型能力限制，本修复只能通过多视角提供更多真实信息。
- 线上服务器尚未部署本次修改，需要拉取代码并重启服务后才会生效。

## 经验教训

1. **“前端看起来有文件”不等于服务端有文件**。多轮能力必须同时检查请求体、草稿持久化和模型输入三处。
2. **提示词不能修复接口契约**。图生 3D 不接收文字时，再强的提示词也不会改变几何；要改结构只能换生成路线。
3. **复合输入要先拆再送**。多视图 API 要的是多个槽位，不是一张包含多个视角的图片；本地确定性拆分比让服务猜更可靠。
4. **不确定时明确阻止，比静默产出错误模型好**。三视图拆分失败时停止提交，用户能立刻知道该怎么做，而不是拿到 3 个人物。
