# Fix Report - 函数模板点击即发送、改解析式后视窗不联动及同类表单细节

## Bug 描述

用户反馈了三个直接问题，并要求继续审计同类细节：

1. 点击首页“函数图像”示例后，系统立刻把固定的 `y=x^2-2x-3` 发送出去，用户没有机会填写自己的函数；
2. 确认卡允许修改函数解析式，但修改后下面的 `x 最小 / x 最大 / y 最小 / y 最大` 和关键点不会跟着变化；
3. 用户无法判断旧视窗是否会破坏正确性，也不知道自动视窗和手动视窗分别该信谁。

继续审计时还确认了以下同类问题：

- 连续修改解析式时，多个预览请求可能乱序返回，旧结果会覆盖新结果并重新启用生成按钮；
- 自动视窗已经开启时，裁切提示仍建议“勾选自动视窗”，属于自相矛盾；
- `sqrt(x)`、`ln(x)`、`asin(x)` 的自动视窗会把定义域外的空白区域也算进去，曲线挤在一侧；
- 手动视窗裁切时只提示“可能裁切”，没有给出裁切比例；
- 修改解析式后，确认清单里仍保留旧范围、旧坐标的问题；
- 手动模式反复预览会重复追加同一段视窗说明；
- 三维文件未上传时仍可能点亮“生成”按钮；
- 清空中文标题后，场景仍会沿用分析阶段的中文标题；
- 模板弹层在“上一条仍在处理”时先关闭弹层再报错，用户输入被清空。

## 问题根因

### 1. 示例卡把“示例”做成了“提交”

旧实现的示例按钮携带一条完整提示词，点击后直接进入分析流程。固定解析式因此被当成用户已经确认的输入，既没有留出编辑机会，也没有“只填入输入框”的中间状态。

### 2. 确认卡只改了 DOM，没有重算数据源

解析式输入框和 x/y 输入框只是普通表单控件。修改解析式后：

- 前端没有请求新的视窗；
- 后端分析阶段生成的 `x_min/x_max/y_min/y_max/key_points` 仍是旧值；
- 生成时如果直接使用这些旧字段，几何引擎就会按旧视窗绘制新函数。

这不是单纯的显示问题。旧视窗会造成两类正确性风险：

- **裁切**：新函数的零点、顶点或整段曲线落在旧 y 范围之外，板面上只剩一小段；
- **漏标**：关键点按旧窗口过滤，零点/顶点不会出现在触觉板上，但用户以为已经标了。

### 3. 预览请求没有序号，存在竞态

用户快速输入 `x^2`、`x^2-2x-3` 时会产生多个请求。网络返回顺序不保证与输入顺序一致，旧响应可能最后到达，把新视窗覆盖掉。只做防抖不能彻底解决，因为防抖只减少请求数量，不保证响应顺序。

### 4. 自动视窗和手动视窗的语义没有在 UI 上说清

后端在 `auto_window=true` 时会完全忽略客户端传来的 x/y 并重新计算；手动模式则必须尊重用户填写的范围。旧提示没有区分这两种情况，于是自动模式也会出现“请勾选自动视窗”的矛盾文案。

### 5. 自动取景只按特征范围扩边，没有考虑定义域边界

`suggest_window()` 先按零点/极值取景，再统一加边距。对 `sqrt(x)`、`ln(x)` 这类单侧定义域函数，左侧边距会落到无定义区域，曲线被挤到右侧；对 `asin(x)` 则会超出 `[-1, 1]`。

### 6. 其他表单只做了“能点”，没有做“该不该点”

- 三维卡片没有检查 `mesh_path`，空文件也能进入生成；
- 场景覆盖值只在有中文标题时写入，清空后没有删除旧 `title_zh`；
- 模板弹层先关闭再检查 `state.sending`，报错时输入已经被清空。

## 尝试记录

### 尝试 1：只把示例提示词改成占位符，点击后仍直接发送

- 结果：失败
- 原因：用户仍然没有机会填解析式；问题不在提示词内容，而在点击行为。

### 尝试 2：解析式 `input` 事件里同步改 x/y 文本

- 结果：失败
- 原因：前端没有可靠的取景算法，照抄旧范围或粗略估算都会和最终几何不一致；关键点也无法在前端可靠重算。

### 尝试 3：加防抖，但不校验响应序号

- 结果：失败
- 原因：防抖减少了请求，但慢的旧请求仍可能后到；必须给每次编辑分配递增序号，并在响应回来时比对。

### 尝试 4：预览和生成各自维护一套窗口逻辑

- 结果：失败
- 原因：两套逻辑迟早漂移。最终让 `/api/function-preview` 和最终构建共用 `_function_window()`，预览看到的就是构建使用的窗口。

## 最终方案

### 示例卡只填入，不发送

- 首页“函数图像”示例改为 `把函数 y=@@ 做成 A5 触觉板，标出零点和顶点。`；
- `prefillComposer()` 去掉 `@@` 占位符，把光标放到 `y=` 后面，并提示“已填入输入框，请在 y= 后填写你的函数”；
- 示例区增加说明：“点击示例只会填入下方输入框，不会直接发送”；
- 发送前增加空解析式校验，`y=` 后面没填内容时阻止发送并聚焦输入框。

### 解析式联动视窗

- 新增 `POST /api/function-preview`，输入解析式和可选窗口，返回规范化解析式、实际 x/y 窗口、关键点、裁切比例和警告；
- 前端在解析式输入后 360ms 防抖请求预览；
- 自动视窗下，x/y 输入框设为只读并显示为虚线派生值，避免用户误以为可以单独改一个；
- 手动模式下，x 必须成对填写；y 可以两项都留空，由当前 x 区间自动计算；
- 预览成功后同时更新 x/y 输入框、关键点表、视窗状态、裁切提示和确认清单；
- 构建接口和预览接口共用 `_function_window()`，自动模式在构建时也会忽略残留的旧 x/y。

### 竞态处理

每次调度预览时立即递增 `state.seq`，响应返回后只有序号仍匹配才允许写入 DOM。旧请求不会覆盖新结果，也不会提前把生成按钮重新点亮。

### 正确性提示

- 手动视窗裁切时显示具体比例，例如“当前 y 视窗会裁掉约 10.5% 的曲线采样点”；
- 自动视窗裁切时说明这是“按分位数避开极端值的自动取景”，并引导用户取消自动视窗后手动扩大范围，不再建议重复勾选自动视窗；
- 解析式为空、x 不成对、上下界颠倒、y 只填一项时，生成按钮直接禁用并给出原因；
- 预览请求未返回前禁止生成，避免用旧窗口抢跑。

### 定义域取景

`suggest_window()` 增加 `_defined_x_extent()`：在候选窗口内采样，找到第一个和最后一个有定义的 x；如果边界外侧留白超过窗口宽度的 8%，就把边界收回到定义域附近。结果：

- `sqrt(x)`：`x∈[-0.025, 5]`；
- `ln(x)`：`x∈[-0.005, 4]`；
- `asin(x)`：`x∈[-1.005, 1.005]`；
- `1/x`、`tan(x)` 仍保留极点两侧，不会被误裁成单侧。

### 确认清单不再保留旧数字

- 前端删除含旧范围、旧坐标、旧“修改解析式”提示的清单项；
- 每次预览只保留一条带 `data-function-guidance` 的视窗说明，先删旧再插新，避免手动模式反复追加；
- 顶点与零点重合时，动态追加“希望用何种触觉标记区分”的问题。

### 同批审计修复

- 三维卡片没有 `mesh_path` 时禁用生成，并在覆盖值收集时再次拒绝；
- 场景英文标题被清空时删除旧 `title_zh`，不再静默沿用分析阶段的中文标题；
- 模板弹层先检查 `state.sending`，再关闭弹层和清空输入；
- 参数化折线裁剪保留原始端点，简化时用最后采样点替换过短的尾点，避免抛物线顶点产生约 0.1 mm 的碎片三角形；
- 极点、阶跃函数、下溢尾部不再被误判为极值或大量零点。

## 经验教训

1. “示例”按钮的默认行为必须是**填入**，不是提交；只要它替用户做了不可见的决定，用户就会觉得系统在自作主张。
2. 可编辑字段背后必须有一条完整的重算链路。只改输入框、不重算依赖字段，比不让改更危险，因为界面看起来是对的。
3. 防抖解决请求频率，序号解决请求顺序，两者不能互相替代。
4. 自动模式和手动模式要有不同的提示语；让用户“开启已经开启的功能”会直接摧毁提示的可信度。
5. 取景算法必须知道函数的定义域。只按采样值扩边，会把 `sqrt(x)`、`ln(x)` 画成偏在一角的曲线。
6. 表单校验要同时做在按钮状态和提交收集两处；只禁用按钮挡不住程序化调用，只在提交时报错则用户会多点一次。
7. 几何正确性不只取决于主算法，浮点裁剪和折线简化留下的小数级尾点，足以让网格最小边检查失败。
