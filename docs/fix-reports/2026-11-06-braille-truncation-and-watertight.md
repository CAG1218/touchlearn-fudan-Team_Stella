# Fix Report - 盲文“看不懂”与 high 档水密检查过慢

日期：2026-11-06　版本：v0.3.4

## Bug 描述

用户完成一次 `standard` 档的三维生成后反馈：

1. 底座上的盲文只有很少几个点，看不懂是什么意思；
2. 怀疑这些点是“乱码”或模型随手生成的装饰；
3. 顺带要求把重复的水密检查优化掉，让 `high`（约 100 万面）也能在 2 vCPU / 4 GiB 上稳定跑完。

截图里底座铭牌的点数明显少于界面显示的“站立小狗”应有的点数。

## 问题根因

盲文点阵本身不是随机生成的：`cnbraille` 按 GF 0019-2018 查拼音表、再编码声母/韵母/声调，`站立小狗` 确定为 10 个单元、28 个点。真正的问题是**排版阶段静默截断**：

1. `compose_printable()` 先用 60 mm 宽度把标题截成“站立小”，铭牌又用更窄的宽度截成“站立”或“站立小”；
2. 铭牌原先只有 18 mm 深，四字标题放不下一行，代码直接丢字而不是换行；
3. `meta` 里的标题仍写成完整标题，界面和 README 因此与实物不一致；
4. 图例用 `f"{index}{text}"` 把编号和第一个音节拼在一起，没有空格单元分隔，读起来更像“乱码”；
5. `"dots": 0` 只是占位值，从未真正统计点数。

水密检查慢的根因是多趟全网格扫描叠加：

1. `edge_counts()` 用“点坐标元组”当字典键，100 万面会创建约 150 万个巨型键；
2. `bounds()` 先生成三个 300 万元素的临时列表；
3. `stats()`、`_print_settings()`、`standards.py` 各自再扫一遍网格；
4. `compose_printable()` 同时持有源网格、变换网格和合并网格三份数据。

## 尝试记录

### 尝试 1：只把点径调大

- 结果：失败
- 原因：点少不是因为点小，而是标题被截断，调大点径只会让缺点更明显。

### 尝试 2：让大模型生成盲文点阵

- 结果：放弃
- 原因：大模型无法保证 GF 0019-2018 的确定性编码，也无法保证同一次输入每次输出一致；这会真正引入“随机点”。正确做法是保留内置码表，只补可核验的解码展示。

### 尝试 3：缓存 + 单趟拓扑 + 合并变换

- 结果：成功
- 原因：`Mesh` 增加按三角面数量失效的缓存；`bounds/volume/topology` 只算一次；边键改成两个 32 位顶点编号折叠成一个 64 位整数；模型变换和抬高一次完成，三角面元组复用。
- 本机 98 万面索引网格基准：读取 GLB 0.74 s、`compose_printable` 2.17 s，端到端峰值 RSS 942 MB。
- 非索引最坏情况（100 万面、300 万顶点）：读取 1.31 s、组装 2.30 s，端到端峰值 1.38 GB，仍低于 4 GiB。

### 尝试 4：标题自动换行 + 可视化解码

- 结果：成功
- 原因：铭牌加深到 26 mm，标题按 1–3 行均衡换行（四字标题为“站立 / 小狗”）；确实放不下时在 `meta` 和界面明确标记 `title_truncated`，不再静默丢字。打印卡新增 2×3 点格、拼音和点号对照，README 同步输出同样内容。

## 最终方案

- `cnbraille.describe_text()` 输出每一个印刷单元（含数字、空格、标点），供界面和 README 解码；
- 底座铭牌支持 1–3 行均衡换行，标题不再被 60 mm 单行截断；
- 图例编号与名称之间插入空格单元；
- `meta.braille` 记录 `title_lines`、`title_cells`、`title_dots`、`pinyin`、`title_truncated` 和图例的完整点阵/拼音；
- 前端打印卡和 README 都显示“盲文对照（给明眼人看）”；
- 标题或标签含码表未收录的生僻字时，在调用三维服务前抛出可读错误，避免浪费 3–4 分钟；
- 水密/体积/包围盒改为缓存单趟计算，GLB 解析不再复制整个二进制块，索引和顶点各用一条直读路径。

## 经验教训

1. “看起来像乱码”往往不是编码错误，而是**展示层与实物不一致**；先比对元数据、界面和实际几何，再怀疑编码。
2. 任何“放不下就截断”的隐式兜底都必须留下可见标记，否则用户会把截断结果当成完整内容。
3. 百万面网格的问题通常不是算法复杂度，而是**重复扫描和临时对象**；先量化峰值内存，再决定改哪里。
4. 确定性编码不能用生成式模型替代；生成式模型适合命名和描述，不适合需要逐点核验的标准点阵。
