# Fix Report - 三维建模请求在写出正文前耗尽输出额度

## Bug 描述

在线上版（v0.3.0）上传 `尾翼图.png` 并选择 `DeepSeek-V4-Pro · 思考高` 后，页面提示：

> 我读到了三维建模需求，但还不能可靠地排成模型：模型在写出正文前耗尽了 max_tokens（finish_reason=length），通常是推理过程占满了输出预算。请提高 max_tokens 或降低推理强度。

用户的 API Key 本身没有设置 token 用量限制，因此这不是账号配额问题，而是应用自己给单次回答设置的上限太小。

## 问题根因

1. `src/touchlearn/model3d.py` 调用 `chat_json(..., max_tokens=4096)`。`max_tokens` 是**单次响应**的输出额度，不是账号配额；思考型模型的隐藏推理 token 也计入这个额度。用户选择“思考高”时，4096 在模型写出第一个正文 token 之前就被推理过程消耗完，返回 `finish_reason=length` 和空内容。
2. `src/touchlearn/agent/llm.py` 的 `chat()` 默认值是 `max_tokens=1800`，并且总是把该字段写进请求。其余调用点还散落着 1200、1400、2400、4096、8192 等小上限。
3. `plan_model3d` 没有针对 `finish_reason=length` 的重试；分类、读图、场景生成等路径虽有“降低思考强度重试”，但三维建模路径没有。
4. 面向用户的错误文案直接暴露 `max_tokens` 术语，并把“提高 max_tokens”当成用户需要处理的事情。

## 尝试记录

### 尝试 1：确认是否为账号配额

- 结果：排除。
- 原因：TokenHub 官方模型列表给出 DeepSeek 系列最大输出 384k tokens；用户 Key 也没有设置用量限制。失败发生在我们请求的 4096 上限，而不是服务商配额。

### 尝试 2：只把三维建模的 4096 调大

- 结果：不采用。
- 原因：同类问题在分类、读图、场景 JSON、电路编辑等路径都存在；只改一处会留下同样的隐患，而且 `chat()` 仍会覆盖调用方未显式传入的默认值。

### 尝试 3：统一输出预算 + 自动重试（最终方案）

- 结果：成功，268 项测试通过。

## 最终方案

- `llm.py` 增加按服务商划分的输出预算：TokenHub 65536、DeepSeek 32768、OpenAI 16384，其余按模型能力取 4096–16384；未知服务商回退到 8192。
- `chat()` / `chat_text()` / `chat_json()` 的 `max_tokens` 改为可选参数：
  - 不传：使用服务商预算；
  - `0`：完全不发送 `max_tokens` 字段，把上限交给服务商；
  - `TOUCHLEARN_MAX_OUTPUT_TOKENS` 可统一覆盖，`0` 同样表示不发送。
- `chat_json()` 在 `finish_reason=length` 时自动把额度翻倍重试一次（不超过服务商上限；TokenHub 最高 131072）。
- `plan_model3d()` 增加第二层兜底：若仍被截断，则关闭隐藏思考再试一次，并在成功时把“已自动降低思考强度重试”写入 notes。
- 移除分类、读图、场景、重建、电路编辑等调用点上的 1200/1400/2400/4096/8192 小上限，统一交给传输层。
- 用户可见错误不再出现 `max_tokens` 字样，也不再要求用户自己去调参数。
- `.env.example` 与 `providers_payload()` 增加 `TOUCHLEARN_MAX_OUTPUT_TOKENS` 说明。

## 检查清单

- [x] 检查模块：`agent/llm.py`、`model3d.py`、`agent/scene.py`、`agent/router.py`、`agent/vision.py`、`agent/reconstruct.py`、`agent/scene_edit.py`。

## 经验教训

- `max_tokens` 是单次响应预算，不是 API Key 配额。排查“额度不够”类报错时，先区分账号配额、模型上下文和单次输出预算。
- 对思考型模型，结构化 JSON 任务应同时具备“足够大的预算”和“关闭思考的兜底重试”，只靠调大其中一个仍可能在极端输入下失败。
- 传输层应集中管理预算，不能让每个调用点各写一个小数字；否则同类问题会反复出现。
- 面向用户的错误文案不应暴露内部参数名，更不应把参数调整责任推给用户。
