# Feature Report - 移除访问码，改用手机号/邮箱验证码账号中心

## 需求描述

用户要求把“访问码”整套机制删掉，换成类似 Chatbox / WorkBuddy 的账号体系：

1. 其他用户访问智能体时不再输入共享访问码；
2. 用手机号验证码或邮箱验证码登录；
3. 第一次验证通过自动注册并登录，不设密码；
4. 每个手机号或邮箱只能对应一个账号；
5. 手机号和邮箱可以绑定到同一个账号，绑定后两者都能登录；
6. 提供账户中心与设置页，可改昵称、绑定/解绑、退出登录、查看账号状态。

## 问题根因

### 1. 访问码是“共享口令”，不是“用户身份”

旧实现只有一个 `TOUCHLEARN_ACCESS_CODE`，登录后写一个固定 Cookie。它能挡住陌生人，但无法回答“这是谁”：

- 所有人共用同一个身份，无法区分用户、无法做个人设置；
- 改一次访问码会让所有已登录设备同时失效；
- 访问码一旦被转发，就无法单独撤销某个人；
- 前端只有“输入访问码”一个输入框，没有账户概念。

### 2. 账号需要“多对一”的联系方式模型

手机号和邮箱都可能成为登录入口，但两者又可能属于同一个人。用“账号表里放 phone/email 两列”无法满足：

- 同一手机号不能注册两个账号；
- 同一邮箱不能注册两个账号；
- 一个账号最多一个手机号 + 一个邮箱；
- 绑定后两种方式都要能登录；
- 解绑后不能把账号变成无法登录的孤岛。

因此需要独立的 `identities(kind, value)` 表，并对 `(kind, value)` 建全局唯一约束。

### 3. 验证码不能明文落库

验证码是短期凭证。如果直接存明文，数据库泄露或备份外流就等同于账号泄露。会话令牌同理。

## 尝试记录

### 尝试 1：保留访问码，在其上叠加账号

- 结果：失败
- 原因：用户明确要求删掉访问码；两套入口并存会让登录页出现“先输访问码再登录”的双层门槛，体验更差。

### 尝试 2：把访问码当密码，手机号/邮箱只做标识

- 结果：失败
- 原因：仍然需要部署者分发口令，且用户无法自助注册；与“任意用户直接访问”的目标冲突。

### 尝试 3：账号表直接存 phone/email 两列

- 结果：失败
- 原因：无法表达“手机号和邮箱各自全局唯一”，也无法在解绑、换绑时保留历史验证状态；最终改为独立 `identities` 表。

### 尝试 4：验证码只存哈希，不存 salt

- 结果：失败
- 原因：6 位数字空间太小，单纯 SHA-256 可被穷举；最终使用 `auth_secret + salt + kind + value + purpose + code` 的 HMAC-SHA256。

## 最终方案

### 后端账号库

新增 `src/touchlearn/agent/accounts.py`，只使用标准库：

- SQLite 表：`users`、`identities`、`verification_codes`、`sessions`、`meta`；
- `identities(kind, value)` 全局唯一，保证一个手机号/邮箱只属于一个账号；
- 一个账号最多绑定一个手机号和一个邮箱；
- 删除最后一个登录方式会被拒绝（409），避免账号失联；
- 验证码：6 位数字、10 分钟有效、最多尝试 5 次、60 秒重发冷却、单标识 8 次/小时、单 IP 40 次/小时；
- 验证码以 HMAC-SHA256 摘要存储，成功使用后标记 `consumed_at`，不能复用；
- 会话令牌 `secrets.token_urlsafe(32)`，数据库只存 SHA-256 摘要，Cookie 为 `HttpOnly; SameSite=Lax`，HTTPS 下自动加 `Secure`，默认 30 天；
- 首次验证自动创建 `users` 行和 `identities` 行；并发注册时用唯一约束兜底，输家回滚并复用赢家账号。

### 验证码通道

- 邮件：标准库 `smtplib` + `EmailMessage`，支持 `ssl`(465)、`starttls`(587)、`none`（内网中继）；
- 短信：阿里云 `dysmsapi` RPC 签名请求，模板变量按 `code` 传递；
- 两者都未配置时进入开发模式：验证码打印到服务端控制台，并通过 `/api/auth/request-code` 返回给页面自动填入；
- 显式 `TOUCHLEARN_AUTH_DEV_MODE=false` 时，不再回退开发模式；没有通道就明确提示“部署者尚未配置短信或邮件通道”。

### HTTP 路由

- `POST /api/auth/request-code`：登录验证码；
- `POST /api/auth/login`：校验并自动注册，写会话 Cookie；
- `GET /api/auth/me`：当前用户；
- `POST /api/auth/logout`：删除会话并清 Cookie；
- `POST /api/auth/link-code` / `link`：绑定另一种联系方式；
- `POST /api/auth/unlink`：解绑，保留至少一种方式；
- `POST /api/auth/profile`：修改昵称；
- 所有 POST 增加同源 `Origin` 校验，跨站请求返回 403；
- 旧的 `/api/login`、`TOUCHLEARN_ACCESS_CODE`、CLI `--access-code` / `--new-code` 全部删除，仅保留清理旧 `touchlearn_access` Cookie 的兼容逻辑。

### 前端

- 登录页改为手机号/邮箱两个 Tab，输入联系方式 + 6 位验证码；
- 开发模式下验证码显示在页面上并可一键填入；
- 登录成功后右上角显示昵称首字头像，点击打开账户中心；
- 账户中心包含：昵称修改、手机号/邮箱绑定与解绑、账号编号、注册时间、应用设置、退出登录；
- 未配置的通道显示“未开通”，只有一个登录方式时显示“唯一登录方式”，不提供会把自己锁死的解绑按钮；
- 设置页原来的“访问控制”改为“登录账号”，显示当前账号并可打开账户中心。

### 部署与文档

- `deploy/.env.example`、根 `.env.example`、`render.yaml` 移除访问码，加入账号库、开发模式、SMTP 和阿里云短信配置；
- `deploy/deploy.sh` 拒绝开发模式上线，并要求至少一种真实验证码通道；
- Docker 的 `/app/outputs` 持久卷同时保存作业和 `accounts.sqlite3`；
- README、`docs/deploy.md`、`deploy/README.md`、`deploy/mainland.md`、`docs/run_windows.md` 全部改为账号登录说明；
- 历史修复报告保留原文，并加一行迁移说明，避免旧文档与当前行为冲突。

## 经验教训

1. 共享访问码适合“只给自己人看”的演示，不适合“任何用户直接使用”的产品；账户体系一旦要做，就必须把身份、会话和注销链路一起做完整。
2. 手机号和邮箱不是账号表的两列，而是独立的身份实体；用独立表 + 全局唯一约束，绑定、解绑和换绑才有清晰语义。
3. 6 位验证码不能只做普通哈希，必须加服务端密钥和随机 salt；否则数据库泄露后可以被离线穷举。
4. 开发模式必须“默认可用、显式可关、上线必关”。只在文档里写警告不够，部署脚本要直接拒绝开发模式上线。
5. 登录页和账户中心要考虑“通道未配置”“只有一个登录方式”“身份已被占用”这些边界，否则用户会在页面里点出一个无法恢复的状态。
6. 测试要同时覆盖服务层和 HTTP 层；Cookie、Origin 校验、401/403/409 这些行为只有走真实请求才会暴露。
